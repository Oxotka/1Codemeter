# Работа с MongoDB

Этот документ описывает использование MongoDB для хранения статистики по коммитам 1С репозитория.

## Установка MongoDB

### macOS
```bash
brew tap mongodb/brew
brew install mongodb-community
brew services start mongodb-community
```

### Linux (Ubuntu/Debian)
```bash
sudo apt-get install mongodb
sudo systemctl start mongodb
```

### Windows
Скачайте установщик с [официального сайта MongoDB](https://www.mongodb.com/try/download/community)

## Настройка

1. Установите зависимости:
```bash
pip install -r requirements.txt
```

2. Настройте подключение к MongoDB в `src/settings.py`:
```python
def mongo_connection_string():
    # По умолчанию: 'mongodb://localhost:27017/'
    # С аутентификацией: 'mongodb://user:password@localhost:27017/'
    return 'mongodb://localhost:27017/'

def mongo_database_name():
    # Имя базы данных
    return 'codemeter'
```

3. Настройте путь к репозиторию в `src/settings.py`:
```python
def path_to_repo():
    return '/путь/к/вашему/репозиторию'

def name_of_src():
    return 'имя/src/'
```

## Разовое сканирование репозитория

Для разового сканирования всего репозитория (с 2011 года) используйте скрипт `scan_repository.py`:

```bash
python3 scan_repository.py
```

### Особенности:

1. **Возобновление после прерывания**: Скрипт запоминает последний обработанный коммит. Если вы прервете выполнение (Ctrl+C), при следующем запуске он продолжит с того места, где остановился.

2. **Пропуск уже обработанных коммитов**: Скрипт автоматически пропускает коммиты, которые уже есть в базе данных.

3. **Прогресс**: Отображается прогресс-бар с информацией о количестве обработанных коммитов и файлов.

4. **Обработка ошибок**: Если при обработке конкретного коммита возникает ошибка, скрипт продолжает работу с следующим коммитом.

## Структура данных в MongoDB

### Коллекция `commits`

Каждый документ содержит информацию об изменении одного файла в коммите:

```javascript
{
  "_id": ObjectId("..."),
  "sha": "a1b2c3d4e5f6...",           // SHA коммита
  "date": ISODate("2023-01-15T10:30:00Z"),
  "file": "src/CommonModules/Модуль/Module.bsl",
  "type": "CommonModules",              // Тип объекта
  "object": "Модуль",                   // Имя объекта
  "content": "Module",                  // Дополнительный путь (если есть)
  "subsystems": ["Подсистема1", "Подсистема2"],  // Список подсистем
  "insert": 25,                         // Добавлено строк
  "delete": 10,                         // Удалено строк
  "email": "developer@example.com",
  "name": "Иван Иванов",
  "message": "Исправление бага...",     // Сообщение коммита (до 500 символов)
  "committed_date": ISODate("2023-01-15T10:30:00Z"),
  "authored_date": ISODate("2023-01-15T10:25:00Z"),
  "created_at": ISODate("2024-01-20T12:00:00Z")  // Когда запись была создана
}
```

### Коллекция `authors`

Информация об авторах коммитов:

```javascript
{
  "_id": ObjectId("..."),
  "email": "developer@example.com",
  "name": "Иван Иванов",
  "updated_at": ISODate("2024-01-20T12:00:00Z")
}
```

### Коллекция `metadata`

Метаданные для управления процессом сканирования:

```javascript
{
  "_id": ObjectId("..."),
  "key": "last_processed_commit_sha",
  "value": "a1b2c3d4e5f6...",
  "updated_at": ISODate("2024-01-20T12:00:00Z")
}
```

## Индексы

Для оптимизации запросов созданы следующие индексы:

- `commits.sha, file` - составной уникальный индекс (один коммит может содержать несколько файлов)
- `commits.sha` - индекс для быстрого поиска по SHA коммита
- `commits.date` - индекс для поиска по дате
- `commits.email` - индекс для поиска по автору
- `commits.type, object` - составной индекс для поиска по типу и объекту
- `metadata.key` - уникальный индекс для метаданных

## Примеры запросов

### Получить все коммиты автора:
```python
from src.save_to_mongo import MongoRepository

repo = MongoRepository()
commits = repo.commits_collection.find({'email': 'developer@example.com'})
```

### Получить статистику по типу объекта:
```python
pipeline = [
    {'$match': {'type': 'CommonModules'}},
    {'$group': {
        '_id': '$object',
        'total_insert': {'$sum': '$insert'},
        'total_delete': {'$sum': '$delete'},
        'commits_count': {'$sum': 1}
    }}
]
stats = list(repo.commits_collection.aggregate(pipeline))
```

### Получить последний обработанный коммит:
```python
last_sha = repo.get_last_processed_commit_sha()
```

## Еженедельное обновление

После разового сканирования для еженедельного обновления можно использовать основной скрипт `main.py`, но с включенной опцией MongoDB:

1. В `src/settings.py` установите:
```python
def save_to_mongo():
    return True
```

2. Настройте даты для обработки только новых коммитов:
```python
def date_since():
    # Например, с начала текущей недели
    from datetime import datetime, timedelta
    today = datetime.now()
    week_start = today - timedelta(days=today.weekday())
    return week_start
```

3. Запустите:
```bash
python3 main.py
```

Скрипт автоматически пропустит коммиты, которые уже есть в базе данных (благодаря уникальному индексу на `sha`).

## Параллелизация

### Проблема с текущим подходом

Текущая реализация использует концепцию "последнего обработанного коммита" для возобновления после прерывания. Это работает отлично для последовательной обработки, но **не подходит для параллелизации**, потому что:

1. Коммиты обрабатываются последовательно от начала к концу
2. Сохраняется SHA "последнего" коммита в последовательности
3. При параллельной обработке порядок теряется - коммиты обрабатываются не по порядку
4. Концепция "последнего коммита" теряет смысл

### Альтернативный подход для параллелизации

Параллелизация **возможна**, но требует изменения подхода:

**Вместо отслеживания "последнего коммита":**
- Проверять каждый коммит на существование в БД перед обработкой
- Обрабатывать коммиты параллельно независимо от порядка
- При возобновлении просто пропускать уже обработанные коммиты

**Преимущества:**
- ✅ Можно обрабатывать коммиты параллельно
- ✅ Можно прервать и продолжить (пропустит уже обработанные)
- ✅ Не зависит от порядка обработки

**Недостатки:**
- ❌ Нужно проверять каждый коммит перед обработкой (дополнительные запросы к БД)
- ❌ При возобновлении нужно пройтись по всем коммитам для проверки (но это быстро благодаря индексам)

### Реализация параллелизации (если понадобится)

Если нужно будет добавить параллелизацию, можно использовать такой подход:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
from threading import Lock

def scan_parallel(self, max_workers=4):
    # Получаем все коммиты
    all_commits = list(self.repo.iter_commits(branch))
    
    # Фильтруем уже обработанные коммиты
    commits_to_process = [
        commit for commit in all_commits 
        if not self.mongo_repo.commit_exists(commit.hexsha)
    ]
    
    # Обрабатываем параллельно
    with ThreadPoolExecutor(max_workers=max_workers) as executor:
        futures = {
            executor.submit(self._process_commit, commit): commit 
            for commit in commits_to_process
        }
        
        for future in as_completed(futures):
            commit = futures[future]
            try:
                files_count = future.result()
                # Обновляем статистику
            except Exception as e:
                print(f'Ошибка при обработке {commit.hexsha[:8]}: {e}')
```

**Важно:** При параллелизации нужно:
- Использовать thread-safe операции для MongoDB (pymongo поддерживает это)
- Создавать отдельное подключение к MongoDB для каждого потока
- Или использовать connection pooling

### Рекомендация

Для большинства случаев **последовательная обработка достаточна**, потому что:
- MongoDB и так работает быстро
- Основное время уходит на чтение коммитов из Git, а не на запись в БД
- Последовательная обработка проще и надежнее
- Легче отслеживать прогресс и отлаживать

Параллелизация имеет смысл только для **очень больших репозиториев** (десятки тысяч коммитов), где обработка действительно занимает много времени.
